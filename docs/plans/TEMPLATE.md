# PLAN TEMPLATE

> 用途：给复杂任务写一份可执行、可恢复、可验证的活计划。
>
> 适用场景：
>
> - 预计超过 1 小时
> - 超过 5 个文件
> - 涉及多个 package
> - 涉及重构、迁移、删除、重命名、模块移动
> - 涉及共享契约或回滚风险

---

# PLAN: <任务标题>

## Context

说明这次任务的背景。

建议回答：

- 现在有什么问题
- 这个问题为什么值得现在解决
- 它影响了哪些包、链路或使用方式

## Goal

写清楚这次任务完成后，用户或开发者能观察到的结果。

不要只写“我要改哪些文件”，而要写“最后会变成什么样”。

## Non-Goals

明确这次不做什么。

这部分很重要，它能防止任务在执行中无限膨胀。

## Scope

列出受影响的目录、包和关键模块。

例如：

- `packages/schema`
- `packages/renderer`
- `packages/editor/src/renderer`
- `docs/architecture/`

## Risks

列出这次任务的主要风险和兼容性边界。

建议至少写：

- 会不会破坏共享契约
- 会不会引入回归
- 有没有回滚难点
- 有没有历史路径要灰度保留

## Verification

先写好验证方式，再动手。

仓库级默认命令：

```bash
pnpm -r exec tsc --noEmit
pnpm -r test
pnpm build
pnpm lint
```

如果有更精确的区域验证，也补上。

例如：

- preview smoke test
- codegen snapshot test
- store / simulator 相关测试

## Milestones

每个 milestone 都要满足：

- 有明确结果
- 范围可控
- 可以独立验证

建议格式如下：

### M1 <里程碑标题>

#### 目标结果

- <写这一步完成后应该看到什么>

#### 具体工作

- <列出关键动作>

#### 验证

- `<命令或检查动作>`
- <预期结果>

### M2 <里程碑标题>

#### 目标结果

- <写这一步完成后应该看到什么>

#### 具体工作

- <列出关键动作>

#### 验证

- `<命令或检查动作>`
- <预期结果>

## Progress

按时间或状态维护进度，保持它是活的。

建议格式：

- [ ] M1 <标题>
- [ ] M2 <标题>
- [ ] M3 <标题>

如果中途改了计划，也在这里更新，不要让计划和现实脱节。

## Discoveries

记录执行过程中发现的新信息。

例如：

- 某个隐式耦合原来比预期更深
- 某个边界并不像文档里写的那样稳定
- 某个旧路径仍然被隐藏依赖

## Decision Log

记录关键取舍，而不是只记结论。

建议回答：

- 为什么选这个方案
- 为什么没有选另一条路
- 哪些限制导致了当前取舍

## Rollback

如果这次任务失败，怎么快速回退。

例如：

- feature flag 回退
- 保留旧路径并行一个迭代
- 回到旧协议但不丢新实现

## Outcomes

任务结束后补这一节。

至少写：

- 实际完成了什么
- 和原计划相比有什么偏差
- 哪些风险真的出现了
- 哪些经验需要回写到 `docs/architecture/` 或其他长期文档

## Retrospective

最后补一小段复盘：

- 这次做得好的地方
- 下次可以更早做对的事情
- 哪些规则值得沉淀回 `AGENTS.md`
