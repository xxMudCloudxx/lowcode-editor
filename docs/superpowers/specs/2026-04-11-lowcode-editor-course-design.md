# lowcode-editor 交互式课程设计文档

日期：2026-04-11
主题：将当前 `lowcode-editor` Monorepo 项目转化为中文交互式课程

## 1. 目标

为当前仓库生成一套可直接在浏览器打开的中文交互式课程，帮助读者在面试场景下准确、完整、结构化地讲清楚这个低代码编辑器项目。

课程的首要目标不是“教会读者从零写代码”，而是帮助读者：

- 快速建立对项目整体架构的全貌理解
- 能把拖拽搭建、配置驱动、渲染、出码等关键链路讲清楚
- 在面试中用更专业的语言描述模块职责、数据流和工程亮点
- 知道哪些点值得展开，哪些点适合用一句话收束

## 2. 受众与内容口径

课程受众是希望“把项目讲清楚”的前端候选人，默认具备基础前端经验，但不假设其已经彻底读懂本仓库。

内容口径遵循以下原则：

- 以中文编写
- 先讲用户体验，再讲底层实现
- 同时覆盖“整体架构导览”和“核心机制深挖”
- 输出偏面试表达，而不是偏 API 参考文档
- 所有术语第一次出现时给出平实解释，避免只堆砌名词

## 3. 代码库理解摘要

当前仓库是一个基于 `pnpm workspace` 的 Monorepo，主要包含以下 5 个核心包：

- `@lowcode/schema`：定义共享类型、协议和组件树结构
- `@lowcode/materials`：定义低代码物料及其 `meta/dev/prod` 三层能力
- `@lowcode/renderer`：根据 Schema 将页面递归渲染为 React 组件树
- `@lowcode/code-generator`：将 Schema 进一步转换为可发布的 React + Vite 项目代码
- `@lowcode/editor`：提供可视化编辑器 UI，包括画布、物料区、组件树、配置面板和交互操作

课程将围绕一个完整主线展开：

“用户把一个组件拖到画布中，修改属性，实时看到变化，最后导出为真实前端项目。”

这个主线可以自然串起物料系统、拖拽系统、状态管理、渲染器和出码流水线。

## 4. 输出形态

课程输出为一个可直接打开的静态站点目录，位于：

`docs/courses/lowcode-editor-interactive-course/`

目录中包含：

- `styles.css`
- `main.js`
- `_base.html`
- `_footer.html`
- `build.sh`
- `modules/*.html`
- `index.html`

构建完成后，用户无需启动本地服务即可直接打开 `index.html` 查看课程。

## 5. 课程组织方案

最终采用“体验驱动的架构拆解型”组织方式。

理由：

- 相比纯“面试答题型”，它更像一套真正可浏览的课程，吸引力更强
- 相比纯“源码漫游型”，它更贴近用户已经知道的产品行为，进入门槛更低
- 它最适合把“我做了什么”转化为“这个系统为什么这么设计”

课程结构先建立全貌，再拆关键链路，最后收束为面试表达模板。

## 6. 模块设计

课程总计 6 个模块。

### 模块 1：这个项目到底在解决什么问题

目标：

- 用非技术语言说明低代码编辑器的价值
- 区分“组件库”和“低代码系统”
- 建立完整用户动作主线

内容重点：

- 用户如何通过拖拽和配置搭建页面
- 为什么“能导出源码”是这个项目的关键差异点
- 用一个端到端动作引出后续所有模块

### 模块 2：Monorepo 里的五个主角

目标：

- 讲清五个包各自的边界和依赖关系
- 帮读者形成可复述的架构地图

内容重点：

- `schema / materials / renderer / code-generator / editor`
- 各包解决什么问题
- 为什么 Monorepo 适合这种低代码平台

### 模块 3：拖进去的组件为什么能真的出现在画布上

目标：

- 拆解拖拽到渲染的关键链路
- 讲清“物料系统”和“画布系统”怎么衔接

内容重点：

- 物料注册
- `parentTypes` 反向约束
- 拖拽接收逻辑
- Schema 写入
- Renderer 递归渲染

### 模块 4：右侧属性改一下，页面为什么会立刻变

目标：

- 讲清状态管理与配置驱动 UI
- 让读者能说明“编辑器为什么看起来是活的”

内容重点：

- Zustand store 的角色
- 组件树与选中态
- 动态属性面板
- 数据更新后的即时预览
- 撤销/重做和持久化的工程价值

### 模块 5：为什么它不只会预览，还能导出真正项目

目标：

- 拆解最有面试价值的“出码流水线”
- 让读者能清楚说明 Schema 与代码生成之间的桥梁

内容重点：

- Schema -> IR
- preprocess / plugins / postprocess / publish
- ProjectBuilder / ModuleBuilder 的职责
- 为什么要做成流水线插件架构

### 模块 6：面试里怎么把这个项目讲得又准又高级

目标：

- 把前五个模块压缩成可复述表达
- 提供“亮点说法”和“追问展开点”

内容重点：

- 架构亮点
- 扩展性亮点
- 工程化亮点
- 低代码系统常见追问
- 适合口述的项目介绍模板

## 7. 交互设计

课程必须包含以下交互元素：

- 至少 1 个组件群聊动画
- 至少 1 个数据流动画
- 每个模块至少 1 个代码转人话翻译块
- 每个模块至少 1 个测验
- 每个模块对首次出现的关键术语提供提示说明

本项目拟采用的具体交互如下：

- 模块 2 使用“群聊动画”模拟五个包之间的协作对话
- 模块 3 使用“数据流动画”展示拖拽组件进入画布后的处理链路
- 模块 5 使用第二个“数据流动画”展示导出源码流水线
- 模块 6 使用情境化小测验，模拟面试官追问

## 8. 视觉方向

视觉风格采用“温暖的开发者笔记本”路线：

- 暖白底色，而不是纯白后台
- 强调色避免紫色系，优先选择更稳重的暖橙或偏红色调
- 标题字重更强，正文清晰易读
- 代码块使用深色背景，与正文区形成清晰层次
- 模块背景交替变化，增强长页面阅读节奏

课程需要明显区别于 README 和普通文档，呈现为真正可浏览、可演示的作品。

## 9. 技术实现策略

根据 `codebase-to-course` 的流程，这个仓库属于复杂代码库，原因如下：

- 它是 Monorepo
- 包之间职责分工清晰且相互依赖
- 既有编辑器运行链路，也有出码链路
- 课程模块数为 6，适合先写 briefs 再生成模块

因此采用复杂代码库路径：

1. 分析代码并提炼模块 briefs
2. 复制参考样板文件到课程目录
3. 定制 `_base.html`
4. 根据 briefs 生成 6 个模块页面
5. 运行 `build.sh` 生成 `index.html`
6. 打开并检查课程结果

## 10. 关键代码链路

生成课程时重点提炼以下链路的源码片段：

- `packages/materials` 中物料定义与自动注册机制
- `packages/editor` 中拖拽处理与状态更新逻辑
- `packages/renderer` 中 Schema 到 React 的递归渲染逻辑
- `packages/code-generator` 中 Parser、IR、Plugin、Publisher 流水线
- Monorepo 层面的包依赖与构建顺序

课程不会试图穷举所有文件，而是只选择最能说明架构意图的代码片段。

## 11. 错误处理与风险

主要风险与对应策略如下：

- README 存在编码显示异常
  处理：以实际代码结构和包配置为主，不依赖 README 单一表述

- 仓库较大，文件较多
  处理：只抽取与 6 个模块直接相关的入口文件和关键链路

- 课程容易写成“概念堆砌”
  处理：每个模块都绑定一个具体用户动作或面试问题

- 课程容易写成“文档”而不是“课程”
  处理：强制加入群聊、流转动画、测验、代码翻译和过渡叙事

## 12. 验收标准

生成结果需要满足以下验收标准：

- 课程为全中文
- 课程主目标服务于项目面试表达
- 最终包含 6 个完整模块
- 覆盖拖拽、物料系统、状态管理、渲染链路、出码流水线、面试总结
- `index.html` 可直接在浏览器打开
- 模块内容具有明显互动性，而不是纯静态说明
- 视觉效果区别于普通文档，具备课程展示感

## 13. 非目标

本次课程不包含以下内容：

- 对每个物料组件做逐项 API 文档式说明
- 覆盖所有历史提交或所有 Roadmap 条目
- 为项目补充新的运行功能或源码改造
- 构建英文版课程

## 14. 后续执行

在用户确认本设计文档后，下一步进入课程构建阶段：

1. 读取 `codebase-to-course` 参考文件
2. 创建课程目录
3. 生成 briefs 和模块 HTML
4. 运行构建脚本产出 `index.html`
5. 做一次可打开性和内容完整性检查
