iframe 沙箱是怎么稳定同步的

真正难的不是“放一个 iframe”，而是“在高频拖拽和大节点树更新时怎样既快又不丢状态”。

先记住这条主从关系

主编辑器是 Master，iframe 画布只是副本。所有写操作最终都要回到 Host 执行，再通过 postMessage 把结果同步给 iframe。

握

Ready 握手

先确认 iframe 准备好了，再开始真实同步。

队

离线队列

没准备好时先排队，避免初始化消息丢失。

补

增量 Patch

平时优先发变化补丁，而不是每次都全量同步整棵树。

救

WAL 回放

如果版本断层，优先补发缺失 patch，不行再降级全量快照。

Ready 握手解决的是“第一屏丢消息”

重点不在语法，而在顺序。Host 不会在 iframe 一加载就盲发消息，而是等它 Ready 之后，先清理过期 patch，再重发完整状态，最后才打开实时同步。

CODE 
  private onReady() {
    this.messageQueue = this.messageQueue.filter(
      (msg) => msg.type !== MessageType.SYNC_COMPONENTS_PATCH,
    );
    this.pendingPatches = [];
    this.flushScheduled = false;
    this.syncFullState(() => {
      this.iframeReady = true;
      this.flushQueue();
    });
  }
PLAIN ENGLISH

iframe 一说“我准备好了”，Host 先把已经过期的 patch 消息过滤掉。

再把等待发送的 patch 缓存清空，避免旧增量干扰新的完整状态。

接着立刻发一份完整状态过去。

只有完整状态同步完了，才真正把 iframeReady 打开，并继续发送排队消息。

高频更新时，性能和恢复要一起设计

1
小树就整包发

如果节点不多，直接同步完整状态最简单。

2
大树按 chunk 分片

避免 structured clone 一次处理太多数据，阻塞主线程。

3
平时优先发增量 patch

通过 patchEventBus 和 patch 压缩，把同步成本压低。

4
如果版本对不上，就触发恢复

Renderer 检测 baseVersion 不匹配后，会请求快照或走 WAL 回放恢复。

Note
这组亮点怎么讲更高级

不要只说“用了 iframe 隔离”。更好的说法是：我围绕 iframe 同步设计了握手、离线队列、增量 patch、分片快照和版本恢复策略，重点解决了高频渲染场景下的一致性与性能问题。
