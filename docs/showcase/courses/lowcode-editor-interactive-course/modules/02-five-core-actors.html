Monorepo 里的五个主角

把 schema、materials、renderer、editor、code-generator 的边界讲清楚，后面任何追问都更好接。

五个角色分别干什么

S
schema

定义共享类型、协议和组件树结构，是全项目的共同语言。

M
materials

定义物料的默认属性、setter、事件和出码描述，是零件仓库。

R
renderer

负责把组件树递归渲染成真正界面，是舞台执行层。

E
editor

负责工具栏、物料区、iframe 画布和设置面板，是工作台。

C
code-generator

负责把 Schema 转成 IR，再进入不同 Solution 的出码流程，是成品工厂。

用群聊记忆这五个角色最有效

谁负责定义规则，谁负责准备零件，谁负责工作台，谁负责画出来，谁负责导出成品，这样记比背目录更容易。

S
schema

我先定义组件树和协议，所有包都按这个格式协作。

M
materials

我给每个物料准备默认属性、编辑配置和出码描述。

E
editor

用户在我这里拖拽、配置、预览，我管理交互和状态。

R
renderer

拿到组件树后，我负责把它递归解释成真正的界面。

C
code-generator

最后我把 Schema 送进 IR、Solution 和 Plugin 流水线，导出真实项目。

物料层并不只是“放组件”

这段代码很能说明 materials 和 code-generator 的关系。物料包会把出码描述和少量自定义逻辑打成一个 pack，交给生成器消费。

CODE 
export const antdCodeGenPack: IMaterialCodeGenPack = {
  descriptors: antdCodeGenDescriptors,
  customLogic: {
    Icon: iconCustomLogic,
    Table: tableCustomLogic,
    FormItem: formItemCustomLogic,
  },
};
PLAIN ENGLISH

先把整套 antd 物料的出码能力打成一个包。

大部分组件只靠描述符就够了，比如依赖、标签映射和属性转换。

少数复杂物料再补程序化逻辑，比如 Icon、Table、FormItem。

这让新增物料时更像“注册协议”，而不是“改核心流程”。

Tip
一句面试表达

“我把具体物料知识留在 materials 层，把流程调度留在 code-generator 层，这样新增物料时不会反复改核心流水线。”
