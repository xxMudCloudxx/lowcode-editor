最后一步不是再学新知识点，而是把前面的链路压缩成一套能直接说出口的面试答案。

先给你一版 1 分钟项目介绍

Pitch
可直接复述的版本

“这个项目是一个基于 React 体系的 Schema 驱动型低代码平台。用户可以通过拖拽组件、配置属性、样式和事件的方式快速搭建 Web 原型。架构上我重点做了两条链路：一条是跨框架出码流水线，先把编辑器 Schema 转成通用 IR，再通过 Solution 抽象接入 React 和 Vue 出码；另一条是 iframe 沙箱同步机制，通过 Ready 握手、离线队列、增量 patch、分片快照和版本恢复，解决高频渲染下的同步稳定性问题。”

1

跨框架出码

通过 IR 和 Solution 让 React 与 Vue 共用同一套生成主流程。

2

物料注册机制

把依赖、标签映射、属性重命名和自定义逻辑抽成可注册描述。

3

Worker 异步出码

把重计算下沉到 Worker，并做最新任务优先的取消与超时控制。

4

iframe 沙箱同步

围绕握手、队列、patch、chunk 和恢复机制设计稳定同步方案。

PLAIN ENGLISH

每次点导出，先给这次任务一个新的请求编号。

然后拿当前组件树，交给 Worker 执行真正的出码。

结果回来后，再检查一次它是不是“最新那次任务”。

如果不是，就直接丢弃旧结果，避免覆盖用户刚刚切换后的新状态。

问
问题是什么

比如频繁切换 Solution 时，旧的出码结果可能覆盖新的状态。

解
方案是什么

把出码下沉到 Worker，并用 requestId、取消旧 Worker、拒绝过期 Promise 做最新任务优先。

值
收益是什么

既减少主线程阻塞，又避免旧结果覆盖新状态，交互体验更稳定。

三个高频追问，你可以这样接

Q1
为什么用 iframe？

因为画布需要一个隔离渲染沙箱，既减少样式和事件污染，又能把 Host 作为唯一写端，通过协议做稳定同步。

Q2
为什么先转 IR？

因为 IR 能把页面语义和目标框架解耦，让 React、Vue 通过不同 Solution 共用同一套主流程。

Q3
为什么 Worker 还要做取消和超时？

因为出码是重任务，而且用户可能连续切换方案；如果不做控制，旧结果覆盖新结果或任务卡死都很常见。

Tip
真正拉开差距的不是术语，而是取舍

高质量回答一定要包含：为什么会有这个问题、为什么选这个方案、它带来了什么收益。
