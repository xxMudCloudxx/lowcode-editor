## 一、出码功能（Code Generator）

### 核心架构

采用**流水线（Pipeline）架构**，参考阿里 `lowcode-engine` 设计：

```
Editor Schema → [Parser] → IR → [Generator Plugins] → 代码文件 → [Postprocessor] → 格式化 → [Publisher] → ZIP
```

### 技术亮点

| 模块                | 职责                | 技术点                                        |
| ------------------- | ------------------- | --------------------------------------------- |
| **Parser**          | Schema → IR 转换    | 递归遍历组件树，提取依赖信息                  |
| **ModuleBuilder**   | 单页面代码生成      | 管理 imports、hooks、JSX 代码块               |
| **ProjectBuilder**  | 项目级别聚合        | 生成完整项目结构（package.json、tsconfig 等） |
| **组件元数据映射**  | 编辑器名 → NPM 包名 | `componentMetadataMap` 抽象映射               |
| **Prettier 后处理** | 代码格式化          | 统一代码风格                                  |
| **ZIP Publisher**   | 打包输出            | 使用 JSZip 打包，Blob 下载                    |

### 🎤 面试详细话术（5-6 分钟）

**开场（30秒）**：

> "在低代码编辑器中，用户通过拖拽生成的是一份 JSON Schema。但这份 Schema 只能在编辑器里运行，无法直接部署。所以我设计了一个**出码模块**，能够把 Schema 转换成一个完整的、可独立运行的 React + Vite 项目。"

**架构设计（1分钟）**：

> "架构上我参考了阿里 `lowcode-engine` 的设计，采用**流水线（Pipeline）模式**。整个流程分为三个阶段：
>
> 1. **解析阶段**：Parser 把 JSON Schema 转换成 IR（Intermediate Representation，中间表示）
> 2. **生成阶段**：多个 Generator 插件消费 IR，生成代码文件
> 3. **发布阶段**：Postprocessor 格式化代码，Publisher 打包成 ZIP"
>
> "为什么要引入 IR？因为它**解耦了输入和输出**。假设将来要支持 Vue，我不需要重写 Parser，只需要替换 Generator 插件。这就是**单一职责原则**的体现。"

**插件系统（1分钟）**：

> "插件分成两个层级：
>
> - **组件级插件**：处理单个组件节点，比如 `jsxPlugin` 生成 JSX 代码，`cssPlugin` 生成样式
> - **项目级插件**：处理跨页面的内容，比如 `routerPlugin` 生成路由配置，`packageJsonPlugin` 聚合所有依赖
>
> "每个插件都是一个纯函数，接收 Builder 作为参数，往里面添加代码片段。这种设计的好处是**可测试、可组合**——我可以单独测试某个插件，也可以灵活组合插件流水线。"

**组件元数据映射（1分钟）**：

> "还有一个关键设计是**组件元数据映射**。编辑器里的组件名可能是 `Typography`，但实际 antd 库导出的是 `Typography.Title`、`Typography.Text` 等。
>
> "我用一个 `componentMetadataMap` 来做映射，每个组件有三个核心方法：
>
> - `getTagName(props)` —— 根据 props 动态决定真实标签名
> - `getTransformedProps(props)` —— 过滤掉编辑器专用属性，转换成真实 props
> - `getLogicFragments(props, builder)` —— 生成 useState、useEffect 等逻辑代码

> - **流水线架构** —— 职责分离，易于扩展
> - **IR 中间表示** —— 解耦输入输出
> - **插件化** —— 可测试、可组合

## 二、UI 主题系统 - 设计令牌架构

### 三层令牌体系

```
┌─────────────────────────────────────────────────────────┐
│   组件层（antdTheme.ts）                                 │
│   colorPrimary: semantic.accent.default                 │
├─────────────────────────────────────────────────────────┤
│   语义层（tokens.ts - semantic）                         │
│   accent.default → accent[600]                          │
├─────────────────────────────────────────────────────────┤
│   原始层（tokens.ts - 色阶）                             │
│   accent: { 50, 100, 200, ..., 900 }                    │
└─────────────────────────────────────────────────────────┘
```

### 🎤 面试详细话术（5-6 分钟）

**开场（30秒）**：

> "在做这个低代码编辑器时，我发现 UI 一致性是个大问题——同一个'主色'在按钮里是一个值，在边框里又是另一个值，非常混乱。所以我设计了一套**设计令牌（Design Token）系统**，参考了 Material Design 3 和 Figma 的 Token 架构。"

**三层架构解释（2分钟）**：

> "整个系统分为三层，我称之为**三层令牌架构**：
>
> **第一层：原始令牌（Primitive Tokens）**
> 这是最底层的颜色值，比如 `neutral: { 50: '#fafafa', 100: '#f5f5f5', ..., 900: '#171717' }`。这些是纯粹的颜色值，没有任何语义。我为每个色系定义了 50-900 共 10 个色阶，类似 TailwindCSS 的色板。
>
> **第二层：语义令牌（Semantic Tokens）**
> 这一层赋予颜色**意义**。比如 `semantic.text.primary = neutral[800]`，表示'主要文字颜色'。这层的好处是，如果我要做深色模式，我只需要把 `text.primary` 指向 `neutral[100]`，所有用到它的地方自动变化。
>
> **第三层：组件层（Component Tokens）**
> 这一层是与 UI 库的对接层。我创建了 `antdTheme.ts`，把语义令牌映射到 Ant Design 的 ConfigProvider。比如 `colorPrimary: semantic.accent.default`。这样 Ant Design 的所有组件就自动应用了我的主题。"

**为什么这样设计（1分钟）**：

> "这种分层设计有几个好处：
>
> 1. **单一数据源（Single Source of Truth）**：所有颜色都在 `tokens.ts` 里定义，不会出现硬编码的 `#1677ff` 散落在各处
> 2. **易于主题切换**：换肤只需要替换原始层，语义层自动传播。比如换成蓝色主题，我只需要改 `accent` 色阶，整个应用的主色就变了
> 3. **设计与开发对齐**：这套命名（primary、secondary、danger）和设计师的 Figma 是一致的，沟通成本低"

**技术实现细节（1分钟）**：

> "技术上，我用 TypeScript 的 `as const` 确保令牌值是字面量类型，IDE 能提供完整的智能提示。
>
> 然后我用 CSS 变量把令牌暴露到全局，比如 `--color-accent-600`，这样 TailwindCSS 和手写 CSS 都能用。
>
> Ant Design 这边，我创建了一个 `antdTheme` 对象，符合 ConfigProvider 的 `ThemeConfig` 类型，把语义令牌映射进去。这样所有 Antd 组件——按钮、输入框、弹窗——都自动应用了主题。"

**与 TailwindCSS 的整合（30秒）**：

> "我还把令牌整合到了 TailwindCSS 的 `theme.extend.colors` 里，这样我可以直接写 `className="bg-accent-600 text-neutral-800"`，而这些类名背后用的都是我的令牌系统。保证了原子类和组件库的风格一致。"

**总结（30秒）**：

> "总结一下，这套设计令牌系统体现了：
>
> - **分层抽象** —— 原始、语义、组件三层各司其职
> - **单一数据源** —— 避免颜色硬编码
> - **可扩展性** —— 支持深色模式、多主题切换
> - **工具链整合** —— 与 Ant Design、TailwindCSS 无缝对接"

## 🎓 Zustand 中间件与增量补丁系统完整教程

### 🚀 第一部分：理解 Zustand 的 `set` 函数

#### 1.1 Zustand 基础用法

Zustand 作为一个精简的状态管理库，其核心在于 `set` 函数。最基础的用法如下：

TypeScript

```
const useStore = create((set, get) => ({
  count: 0,
  
  // 方式一：对象式更新（直接提供要合并的新状态）
  increment: () => set({ count: get().count + 1 }),
  
  // 方式二：函数式更新（接收当前状态，返回新状态）
  double: () => set((state) => ({ count: state.count * 2 })),
}));
```

#### 1.2 什么是 `partial`？

`partial` 是 Zustand 的 `set` 函数的第一个参数，它可以是对象或函数。

| **参数签名**             | **描述**                                       |
| ------------------------ | ---------------------------------------------- |
| `set(partial, replace?)` | `partial` 是必需参数，`replace` 是可选布尔值。 |

`partial` 的两种形式：

- **形式 1：对象**

  TypeScript

  ```
  // 直接合并到 state
  set({ count: 10 }) 
  ```

- **形式 2：函数**

  TypeScript

  ```
  // 接收当前 state，返回新 state（或部分 state）
  set((state) => ({ count: state.count + 1 }))
  ```

之所以被称为 **`partial`**（部分），是因为它通常只包含状态的一部分。Zustand 会对其执行**浅合并（Shallow Merge）**：

> **示例：浅合并**
>
> TypeScript
>
> ```
> // 当前 state
> { count: 1, name: "Tom" }
> ```

> // 执行 set
>
> set({ count: 2 })

> // 结果（浅合并）：name 属性被保留
>
> { count: 2, name: "Tom" }

#### 1.3 `undoMiddleware` 为什么要检查 `typeof partial`？

在实现撤销/重做中间件时，检查 `partial` 的类型至关重要：

TypeScript

```
if (typeof partial === "function") {
  // 函数式更新 → 用 produceWithPatches 处理（记录历史）
} else {
  // 对象式更新 → 直接透传（不记录历史）
}
```

- **函数式更新 (`set((state) => {...})`)：** 通常是用户通过 UI 交互触发的**主动修改**（如点击、输入、拖拽），应该被记录到历史记录中。
- **对象式更新 (`set({ xxx })`)：** 通常用于初始化、状态迁移、或者通过 API 间接设置的**非用户操作**，通常不需要被记录。

### ✨ 第二部分：Immer 的 `produceWithPatches`

#### 2.1 为什么使用 Immer？

Immer 库通过引入 **Draft** 概念，极大地简化了 **不可变数据（Immutable Data）** 的更新操作。

| **方式** | **传统不可变更新 (痛苦)**                                    | **Immer (简洁)**                                             |
| -------- | ------------------------------------------------------------ | ------------------------------------------------------------ |
| **代码** | 嵌套对象需要大量展开运算符：  `const newState = { ...state, ... }` | 直接像修改普通对象一样操作 `draft`：  `draft.components[123].props.text = "新文本";` |

Immer 在底层会自动生成正确的、不可变的新状态。

#### 2.2 `produceWithPatches` 的魔法

`produceWithPatches` 是 Immer 提供的特殊函数，它在生成 `nextState` 的同时，还会生成描述变化过程的 **补丁（Patches）** 及其 **逆向补丁（Inverse Patches）**。

TypeScript

```
import { produceWithPatches } from "immer";

const [nextState, patches, inversePatches] = produceWithPatches(
  currentState,
  (draft) => {
    draft.components[123] = { id: 123, name: "Button", props: {} };
  }
);
```

- **`nextState`:** 更新后的完整状态。
- **`patches`:** 描述**“做了什么”**的一系列操作（用于 **重做/Redo**）。
- **`inversePatches`:** 描述**“如何撤销”**的一系列操作（用于 **撤销/Undo**）。

> **Patches 示例**
>
> `patches` 是一个 JSON Patch 数组：
>
> JavaScript
>
> ```
> patches = [
>   {
>     op: "add",                          // 操作类型：add / remove / replace
>     path: ["components", "123"],        // JSON Pointer 路径
>     value: { id: 123, name: "Button" }  // 新值
>   }
> ]
> ```
>
> **InversePatches 示例**
>
> `inversePatches` 是一个 JSON Patch 数组：
>
> JavaScript
>
> ```
> inversePatches = [
>   {
>     op: "remove",                 // 逆操作
>     path: ["components", "123"]   // 移除这个路径
>   }
> ]
> ```

#### 2.3 `applyPatches` 还原状态

Immer 的 `applyPatches` 函数可以根据 Patches 数组，将任何状态还原或推进到新的状态：

TypeScript

```
import { applyPatches } from "immer";

// 撤销：将当前状态应用 inversePatches 得到之前的状态
const previousState = applyPatches(currentState, inversePatches);

// 重做：将当前状态应用 patches 得到之后的状态
const nextState = applyPatches(currentState, patches);
```

### ⚙️ 第三部分：`undoMiddleware` 完整代码解析

`undoMiddleware` 负责拦截组件状态的更新，并利用 Immer 生成补丁。

TypeScript

```
// src/editor/stores/middleware/undoMiddleware.ts

import { produceWithPatches, enablePatches } from "immer";
import { useHistoryStore } from "../historyStore";

enablePatches(); // 启用 Immer 的 patches 功能（必须调用）

export const undoMiddleware =
  (initializer) =>        // ← 1. initializer 是 creator 函数
  (set, get, api) => {    // ← 2. Zustand 传入的标准参数
    
    // 👇 第3步：包装原始的 set 函数
    const wrappedSet = (partial, replace) => {
      const currentState = get();  // 获取当前 state

      // 4. 判断 partial 是函数还是对象
      if (typeof partial === "function") {
        
        const isApplyingPatches = useHistoryStore.getState().isApplyingPatches;

        // 🔑 核心：用 produceWithPatches 执行更新，并获取补丁
        const [nextState, patches, inversePatches] = produceWithPatches(
          currentState,       // 当前 state
          partial             // 用户传入的 draft 函数
        );

        // 5. 只有在 非undo/redo 且 有实际变更 时才记录
        if (!isApplyingPatches && patches.length > 0) {
          useHistoryStore.getState().addPatch(patches, inversePatches);
        }

        // 6. 用原始 set 应用新状态
        set(nextState, replace);
        
      } else {
        // 对象式更新直接透传，不记录历史
        set(partial, replace);
      }
    };

    // 👇 第7步：用包装后的 set 调用 initializer
    return initializer(wrappedSet, get, api);
  };
```

### 📝 第四部分：`historyStore` 完整代码解析

`historyStore` 专门用于管理历史记录栈 (`past` 和 `future`)，以及执行 `undo/redo` 逻辑。

TypeScript

```
// src/editor/stores/historyStore.ts

import { create } from "zustand";
import { applyPatches } from "immer";

export const useHistoryStore = create((set, get) => ({
  past: [],              // 过去的操作（可撤销）
  future: [],            // 未来的操作（撤销后可重做）
  isApplyingPatches: false,  // 标志位：防止 undo/redo 操作被再次记录

  // 添加补丁（每次用户操作后调用）
  addPatch: (patches, inversePatches) => {
    // 各种跳过检查...
    // ...

    set((state) => ({
      past: [...state.past, { patches, inversePatches }],
      future: [],  // ⭐ 关键：新操作开启新分支，必须清空 future 栈
    }));
  },

  // 撤销
  undo: async () => {
    const { past, future } = get();
    if (past.length === 0) return;
    const lastPatch = past[past.length - 1];

    set({ isApplyingPatches: true }); // 设置标志位

    try {
      // 核心：应用 inversePatches 还原状态
      const { useComponentsStore } = await import("./components");
      useComponentsStore.setState((state) => {
        return applyPatches(state, lastPatch.inversePatches);
      });

      // 更新历史栈：将操作移到 future 供重做
      set({
        past: past.slice(0, -1),
        future: [lastPatch, ...future],
      });
    } finally {
      set({ isApplyingPatches: false });
    }
  },

  // 重做
  redo: async () => {
    const { past, future } = get();
    if (future.length === 0) return;
    const nextPatch = future[0];

    set({ isApplyingPatches: true });

    try {
      // 核心：应用 patches 恢复状态
      const { useComponentsStore } = await import("./components");
      useComponentsStore.setState((state) => {
        return applyPatches(state, nextPatch.patches);
      });

      // 更新历史栈：将操作移回 past
      set({
        past: [...past, nextPatch],
        future: future.slice(1),
      });
    } finally {
      set({ isApplyingPatches: false });
    }
  },
  // ... clear function
}));
```

### 🌳 第五部分：为什么新操作必须清空 Redo 栈？

清空 `future` (Redo 栈) 是所有撤销/重做系统的**标准行为**，被称为 **历史分叉（History Forking）** 原则。

#### 场景分析：

1. **初始状态：** `A → B → C`。`past = [p1, p2, p3]`，`future = []`。
2. **执行撤销两次：** 状态回到 `A`。`past = [p1]`，`future = [p2, p3]`。
3. **用户执行新操作 `D`：** 此时时间线发生分叉。

> - **原本的时间线：** `A → B → C`
> - **新时间线：** `A → D`

如果此时不清空 `future`，用户点击重做，系统可能会尝试应用 `p2`（从 `A` 到 `B` 的操作）。但当前状态已经是 `A + D`，应用 `p2` **可能导致冲突或将系统带入无效状态**。

**类比：** 想象你在一个路口按了撤销，倒退了两步。当你执行新动作（走了新的路 `D`）时，**通往旧目的地 `C` 的重做路径就作废了**。

因此，`addPatch` 函数必须确保在新操作发生时：

TypeScript

```
// 关键代码
set((state) => ({
  past: [...state.past, { patches, inversePatches }],
  future: [],  // 必须清空！
}));
```

### 🔄 第六部分：完整执行流程概览

#### 1. 添加组件时（记录操作）：

| **步骤**          | **操作**                                                   | **结果**                                      |
| ----------------- | ---------------------------------------------------------- | --------------------------------------------- |
| **用户操作**      | 调用 `useComponentsStore.getState().addComponent(...)`     | -                                             |
| **Action 内部**   | 调用 `set(draft => { ... })`                               | -                                             |
| **Middleware**    | `wrappedSet` 拦截并调用 `produceWithPatches(state, draft)` | 得到 `nextState`, `patches`, `inversePatches` |
| **History Store** | 调用 `addPatch(patches, inversePatches)`                   | `historyStore.past` 增加新记录，`future` 清空 |
| **Zustand**       | 调用**原始** `set(nextState)`                              | State 更新，组件重渲染                        |

#### 2. 撤销时（应用逆向补丁）：

| **步骤**          | **操作**                                                     | **结果**                   |
| ----------------- | ------------------------------------------------------------ | -------------------------- |
| **用户操作**      | 调用 `useHistoryStore.getState().undo()`                     | -                          |
| **History Store** | 设置 `isApplyingPatches = true`                              | 阻止本次状态更新被再次记录 |
| **History Store** | 调用 `useComponentsStore.setState(state => applyPatches(state, lastPatch.inversePatches))` | -                          |
| **Middleware**    | `wrappedSet` 拦截，因 `isApplyingPatches` 为 true 而**跳过** `addPatch` | -                          |
| **Zustand**       | 原始 `set` 应用还原后的状态                                  | 状态回到上一步             |
| **History Store** | 设置 `isApplyingPatches = false`，更新 `past` 和 `future` 栈 | 完成撤销                   |

### 📚 概念速查表

| **概念**             | **描述**                                                     | **用途**                                                     |
| -------------------- | ------------------------------------------------------------ | ------------------------------------------------------------ |
| `partial`            | `Zustand set` 的第一个参数，可以是对象或函数。               | 中间件用于判断操作类型（是用户行为还是系统行为）。           |
| `produceWithPatches` | Immer 函数，执行更新**同时**生成 `patches` 和 `inversePatches`。 | 撤销/重做系统的核心，生成增量补丁。                          |
| `patches`            | 描述“做了什么”的 JSON Patch 数组。                           | 用于 **重做 (Redo)**。                                       |
| `inversePatches`     | 描述“如何撤销”的 JSON Patch 数组。                           | 用于 **撤销 (Undo)**。                                       |
| `isApplyingPatches`  | `historyStore` 中的标志位。                                  | **关键**：防止 `undo/redo` 时应用 `applyPatches` 再次触发 `undoMiddleware` 记录历史，造成无限循环或错误记录。 |
| **清空 future**      | 新操作发生时清空 `future` 栈。                               | 遵循历史分叉原则，确保重做路径是有效的。                     |

### 🎤 面试详细话术（5-6 分钟）

**开场 - 问题背景（1分钟）**：

> "在低代码编辑器里，撤销/重做是核心功能。最开始我用的是 `zundo` 库，它采用**快照式存储**——每次操作后都保存整个 state 的深拷贝。
>
> "这有两个问题：
>
> 1. **内存占用高**：如果 state 里有 100 个组件，每次操作就存一份 100 个组件的副本
> 2. **不利于协同编辑**：将来如果要做多人协同，快照无法合并，而增量补丁可以用 CRDT 或 OT 算法进行冲突解决
>
> "所以我决定自己实现一套**增量补丁系统**。"

**Immer 的 produceWithPatches（1分钟）**：

> "我用的核心技术是 Immer 的 `produceWithPatches` 函数。它的特点是，在你用 draft 修改状态时，它会自动记录你做了什么修改，生成两个东西：
>
> - `patches`：正向补丁，记录「做了什么」
> - `inversePatches`：逆向补丁，记录「如何撤销」
>
> "比如你执行 `draft.components[123] = newButton`，它会生成：
>
> ```javascript
> patches = [{ op: 'add', path: ['components', '123'], value: {...} }]
> inversePatches = [{ op: 'remove', path: ['components', '123'] }]
> ```
>
> "这个格式叫 **JSON Patch**，是一个 RFC 6902 标准，互操作性很好。"

**中间件设计（1.5分钟）**：

> "接下来的问题是：如何拦截 Zustand 的 `set()` 调用，自动生成补丁？
>
> "答案是**自定义中间件**。Zustand 的中间件本质上是一个高阶函数，包装原始的 `set`。我的 `undoMiddleware` 做了这些事：
>
> 1. 拦截 `set(partial)`，判断 `partial` 是否是函数（Immer producer 风格）
> 2. 如果是函数，调用 `produceWithPatches`，得到新状态和补丁
> 3. 把补丁存到 `historyStore`
> 4. 用原始 `set` 应用新状态
>
> "代码大概是这样的：
>
> ````typescript
> const [nextState, patches, inversePatches] = produceWithPatches(
>   currentState,
>   partial  // 用户的 draft 函数
> );
> useHistoryStore.getState().addPatch(patches, inversePatches);
> set(nextState);
> ```"
> ````

**防递归设计（1分钟）**：

> "这里有个关键问题：当我执行 `undo()` 时，我需要调用 `applyPatches` 把状态回滚。但这又会触发 `set()`，又会被中间件拦截，又记录一次补丁——这就**无限循环**了！
>
> "我的解决方案是加一个**标志位** `isApplyingPatches`：
>
> ```typescript
> // 在 undo/redo 开始时
> set({ isApplyingPatches: true });
> 
> // 执行 applyPatches...
> 
> // 结束时
> set({ isApplyingPatches: false });
> ```
>
> "中间件在拦截时，先检查这个标志位。如果是 `true`，说明当前是 undo/redo 触发的，直接跳过补丁记录。"

**循环依赖处理（30秒）**：

> "还有一个工程问题：`undoMiddleware` 需要引用 `historyStore`，而 `historyStore` 的 `undo()` 又需要引用 `componentsStore` 来应用补丁。这形成了循环依赖。
>
> "我的解决方案是**动态 import**：在 `historyStore` 里用 `await import('./components')` 延迟加载，打破循环。"

**测试覆盖（30秒）**：

> "为了保证可靠性，我写了 13 个单元测试，覆盖了：
>
> - addPatch 记录和过滤逻辑
> - undo/redo 状态回滚
> - isApplyingPatches 防递归
> - 与 componentsStore 的集成
>
> "测试框架用的是 Vitest，配合 `@testing-library/react` 的 `act()` 处理异步状态更新。"

**总结（30秒）**：

> "总结一下，这个增量补丁系统体现了：
>
> - **性能优化** —— 仅存 diff，内存占用降低一个数量级
> - **中间件模式** —— 非侵入式拦截，符合开闭原则
> - **防御性编程** —— 标志位防递归，动态导入解循环
> - **可测试性** —— 13 个单元测试保证质量
> - **可扩展性** —— 增量补丁为未来协同编辑预留了接口"

## 四、iframe 沙盒安全执行用户代码

### 🎤 面试详细话术（4-5 分钟）

**开场 - 安全问题（1分钟）**：

> "低代码编辑器允许用户编写自定义 JavaScript 代码，比如按钮点击后执行一段逻辑。最开始的实现非常危险——直接用 `new Function(userCode)()` 执行用户代码。
>
> "这意味着用户代码可以：
>
> - 访问 `window`、`document`，劫持整个页面
> - 读取 `localStorage`，窃取用户数据
> - 调用 `fetch`，发送数据到恶意服务器
>
> "这是典型的 **XSS 漏洞**。我决定用 **iframe 沙盒**来隔离用户代码。"

**iframe sandbox 原理（1分钟）**：

> "HTML5 的 `<iframe sandbox>` 属性可以创建一个隔离的执行环境。我的做法是：
>
> ```javascript
> const iframe = document.createElement("iframe");
> iframe.sandbox.add("allow-scripts"); // 只允许执行脚本
> // 不加 'allow-same-origin'，所以无法访问父页面
> ```
>
> "在这个沙盒里，用户代码：
>
> - 无法访问父窗口的 `window`
> - 无法操作父页面的 DOM
> - 无法读写 `localStorage`、`cookie`
>
> "但它**可以执行 JavaScript**——这正是我们需要的。"

**安全传递代码（1分钟）**：

> "还有一个坑：我需要把用户代码传递给 iframe。最开始我用模板字符串：
>
> ```javascript
> var userCode = `${escapedCode}`; // 危险！
> ```
>
> "这有个问题——如果用户代码里有 `${...}`，它会在模板字符串解析时就执行，绕过了沙盒！这叫**模板字符串注入**。
>
> "修复方法是用 `JSON.stringify`：
>
> ```javascript
> var userCode = ${JSON.stringify(code)};  // 安全
> ```
>
> "这样即使代码里有特殊字符，也会被正确转义。"

**postMessage 通信（1分钟）**：

> "用户代码可能需要和主页面交互，比如显示一条消息。我用 **postMessage** 实现白名单通信：
>
> 沙盒内：
>
> ```javascript
> parent.postMessage({ type: "showMessage", payload: "操作成功" }, "*");
> ```
>
> 主页面：
>
> ```javascript
> window.addEventListener("message", (e) => {
> if (e.data.type === "showMessage") {
>  message.success(e.data.payload);
> }
> });
> ```
>
> "我只处理白名单里的 `type`（showMessage、goToLink 等），其他一律忽略。这就限制了用户代码能做的事情。"

**总结（30秒）**：

> "总结一下，这个沙盒方案体现了：
>
> - **最小权限原则** —— 沙盒只开放 `allow-scripts`
> - **防注入** —— 用 `JSON.stringify` 代替模板字符串
> - **白名单通信** —— 只允许预定义的 API
> - **超时控制** —— 执行超时自动销毁 iframe，防止无限循环"

## 面试常见追问及回答

**Q: 为什么选择 IR 中间表示？直接生成代码不行吗？**

> "直接生成代码的问题是**耦合太紧**。如果将来要支持 Vue，我需要重写整个 Parser。有了 IR，Parser 只负责提取信息，Generator 只负责生成代码，两者独立演进。这是编译原理里经典的前端/后端分离思想。"

**Q: 增量补丁相比快照，缺点是什么？**

> "增量补丁的缺点是**实现复杂度更高**，特别是跳转到任意历史状态时，需要从头依次应用所有补丁。但对于撤销/重做这种栈式操作，增量补丁是最优解。"

**Q: iframe 沙盒有什么局限？**

> "主要局限是**通信成本**。每次传递数据都要 `postMessage`，而且只能传可序列化的值，不能传函数或 DOM 节点。如果用户代码需要高频操作主页面，性能会是问题。另一个方案是 Web Worker + SES（Secure ECMAScript），但实现更复杂。"

**Q: 这个项目最大的收获是什么？**

> "最大的收获是**架构设计能力**。以前写代码都是想到哪写到哪，做这个项目让我学会了先画架构图、定义接口、再动手实现。比如出码模块的 IR 设计、主题系统的三层令牌，都是先想清楚再写的。这让代码更容易维护和扩展。"

# 🚀 六、物料协议驱动架构：组件纯粹化与能力外置

## 核心架构设计

本架构采用**协议驱动（Protocol-Driven）**设计，将编辑器的核心能力（如拖拽、选中）与物料组件彻底解耦。组件只负责 **UI 渲染**，不感知编辑器环境。

### 架构示意图

Plaintext

```
┌─────────────────────────────────────────────────────────────────┐
│                          EditArea (画布)                         │
│  ┌──────────────────────────────────────────────────────────┐   │
│  │                     DraggableNode                         │   │
│  │     **通过 cloneElement 注入**：                             │
│  │       • ref (用于 react-dnd 拖拽，通过 mergeRefs 合并)     │  │
│  │       • data-component-id (用于事件委托/选中)              │  │
│  │  ┌──────────────────────────────────────────────────────┐ │   │
│  │  │         **纯净组件 (Button/index.tsx)** │  │
│  │  │   • **只负责 UI 渲染**，不感知编辑器                    │  │
│  │  │   • **必须**使用 forwardRef 支持 ref 转发             │  │
│  │  └──────────────────────────────────────────────────────┘ │   │
│  └──────────────────────────────────────────────────────────┘   │
│                                                                  │
│  **事件处理（onClickCapture 捕获阶段）**:                         │
│    • 捕获阶段拦截，编辑器选中优先级最高                          │
│    • 读取 **editor.interactiveInEditor** 决定是否拦截原生事件   │
└─────────────────────────────────────────────────────────────────┘
```

## 🎤 面试详细话术（5-6 分钟）

### 1. 开场 - 问题背景（1分钟）

> “在最开始的架构里，每个物料组件都有两个版本：`dev.tsx` 用于编辑器渲染，里面耦合了 `react-dnd` 的拖拽逻辑；`prod.tsx` 用于预览和出码。这种设计有几个问题：
>
> 1. **代码重复**：同一个组件要维护两份，改一处容易忘另一处。
> 2. **逻辑耦合**：`useDrag` 散落在每个组件里，很难统一升级。
> 3. **出码不一致**：出码器用的是原生 Antd，但 `prod.tsx` 里的增强逻辑丢失了。”
>
> “我决定重构成**协议驱动架构**——组件只负责 UI，编辑器能力统一**外置注入**。”

### 2. 协议设计（1分钟）

> “核心是一个 **`ComponentProtocol`** 接口，分为**三层**：
>
> - **身份层**：`name`、`desc`、`category`，描述组件是什么。
> - **渲染层**：`component`（**纯净组件**）、`defaultProps`。
> - **编辑层**：`editor` 对象，描述组件在编辑器里的行为。
>
> 其中 `editor` 对象有几个关键字段：
>
> TypeScript
>
> ```
> editor: {
>   isContainer: boolean,        // 是否可接收子组件
>   parentTypes: string[],       // 可放入哪些容器
>   interactiveInEditor: boolean // 编辑时是否允许原生交互
> }
> ```
>
> “组件通过**声明式配置**告诉编辑器自己的行为，编辑器引擎根据协议**动态适配**，不再硬编码。”

### 3. 零 DOM 注入（1分钟）

> “另一个关键设计是 **`DraggableNode`**。之前我考虑用 HOC 包一层 `div`，但这会**破坏 CSS 布局**——比如父容器是 Flex，多一层 `div` 就不再是直接子元素了。”
>
> “我的解决方案是用 **`cloneElement`**：
>
> TypeScript
>
> ```
> return cloneElement(childElement, {
>   ref: mergeRefs(nodeRef, childElement.props.ref),
>   'data-component-id': id
> });
> ```
>
> “直接给子组件**注入 `ref`** 和 **`data-component-id`**，不添加任何 DOM 层级。这里还有个细节—— **`mergeRefs`** 是我自己写的 Hook，用来合并多个 `ref`，防止覆盖子组件原有的 `ref`。”

### 4. 事件捕获策略（1分钟）

> “还有一个问题：原来用 `pointerEvents: none` 来阻止组件原生交互，但这**太粗暴**了——比如 Tabs 组件，编辑时需要点击切换标签来预览不同面板。”
>
> “我改用**事件捕获**：
>
> TypeScript
>
> ```
> <div onClickCapture={handleClickCapture}>
>   {/* 组件树 */}
> </div>
> ```
>
> “**捕获阶段**的优先级比冒泡高，即使组件内部调了 `stopPropagation()`，我也能先拦截到。然后根据 **`interactiveInEditor`** 元数据决定是否阻止后续传播——普通组件拦截，Tabs 这种放行。”

### 5. 向后兼容与总结（1分钟）

> “因为项目已有几十个组件，不可能一次全迁移。所以我设计了一个**类型守卫** `isProtocolConfig`，引擎会自动检测配置格式，新协议用 `component`，旧格式用 `dev/prod`，两种模式可以**共存**。迁移可以逐步进行。”
>
> **总结一下**，这个协议驱动架构体现了：
>
> - **组件纯粹化**：只负责 UI，不感知编辑器。
> - **能力外置**：拖拽、选中、悬浮统一注入。
> - **零 DOM 注入**：`cloneElement` + `mergeRefs`，不破坏布局。
> - **精细化控制**：`interactiveInEditor` 支持组件级交互策略。
> - **渐进式迁移**：类型守卫兼容新旧格式。

## ❓ 面试追问及回答

### Q1: 为什么用 `cloneElement` 而不是 Context？

> “Context 适合传递数据，但这里需要**注入 `ref` 和 DOM 属性**。
>
> - **`ref` 不能通过 props 传递**（React 会特殊处理），必须用 `cloneElement` 或 `forwardRef`。
> - 而 `data-component-id` 需要出现在组件的**根 DOM 节点**上，用 Context 还是要在组件内部处理，违背了 '组件不感知编辑器' 的原则。”

### Q2: `interactiveInEditor` 能解决所有交互问题吗？

> “不能。这是个布尔值，只能决定 '**完全拦截**' 或 '**完全放行**'。如果需要更精细的控制，比如 '只放行特定子区域的点击'，可能需要扩展成一个函数或者更复杂的配置对象。但目前的需求布尔值够用了，遵循 **YAGNI** 原则。”

### Q3: `forwardRef` 强制要求会不会增加开发成本？

> “确实增加了一点。但 **`forwardRef` 是 React 的标准模式**，对于组件库来说本就应该支持。我在开发环境加了**运行时检查**——如果组件没有正确转发 ref，控制台会报错提示，帮助开发者尽早发现问题。”
